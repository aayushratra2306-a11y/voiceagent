Phase 3 — booking & tool calling

A bot's timezone was configured correctly and spoken back wrong

TASK 3.5 · 2026-09-07
Symptom
Bot set to Asia/Kolkata, 09:00–18:00 in the UI. On a live call it offered appointment slots and spoke times in UTC — a 2pm booking would have confirmed as 7:30pm to an Indian caller. No error anywhere. The setting looked saved; it was silently ignored.
Root cause
Every phone call spawns its own OS process (one worker per call, so a crash on one call never touches another). That process registers, at startup, which database collections it's allowed to query — a fixed list passed to the ODM's init_db(). Bot had never been on that list, since the day per-call worker processes were introduced — nothing inside a call had ever needed to read a bot document directly; its config crosses into the process as a plain dict instead. The booking feature broke that assumption: it queries Bot.get(...) live, mid-call. That query raised CollectionWasNotInitialized on every single call — and its own try/except caught the error, logged a warning nobody was watching, and silently fell back to hardcoded defaults (UTC, 9–6, 30 min).
Why tests missed it
The test suite runs in a different process — the pytest runner — and that process's own init_db() registers the full model list, Bot included. So in tests, the exact same line of code succeeds, returns the real timezone, and the test correctly asserts correct behaviour. The test wasn't wrong — it was standing somewhere the bug structurally couldn't reach it.
Fix
Added Bot to the call worker's model list. Then wrote a structural regression test — not a behavioural one — that parses the source of every file that runs inside a call, finds every database model it queries, and asserts each is registered. Verified by literally reverting the fix and re-running: both new tests fail and name the exact file at fault.
before: "timezone": "UTC" (config said Asia/Kolkata) after: "timezone": "Asia/Kolkata" — no fallback warning logged
commit 15eebb1

A test that passed for the wrong reason

TASK 3.5 · 2026-09-07
Symptom
There wasn't one — and that's the entry. Asked to book 11pm against a bot that closes at 6pm, the assistant did exactly the right thing: it offered real morning slots instead and never attempted the booking. The test looked like a clean pass.
Root cause
Nothing forced that behaviour. The opening and closing hours were consulted in exactly two functions — the two that answer "what could I offer?" — and in neither of the two that answer "do it". The assistant only ever proposed in-hours times because the list it was reading from was already filtered; it was never prevented from booking one. A caller pushing past that offer — "book it anyway, 11pm, I don't care" — reaches the booking function directly with a time nothing ever validated.
Why tests missed it
Every existing test drove the booking function with times taken from the available-slots list, because that's what the system produces in normal use. None passed a time from outside that list — so nothing ever probed whether the boundary was actually defended or merely never approached.
Fix
A server-side hours check on both entry points, refusing with real alternatives rather than a bare "no". Proven rather than argued — with the check disabled, the test run logs the appointment landing at 11pm:
[BOOKING] Rescheduled 4L74 to 2026-09-08T17:30:00+00:00 ^ 17:30 UTC = 23:00 India time
The principle worth carrying: a business rule that holds only because of an assumption about how the caller will behave is not enforced, it is hoped for. The language model is not a validation layer — it is the untrusted input.
commit 64eec0b

Rollback logic existed but could never fire

TASK 3.4 · 2026-09-05
Symptom
A tool call that should have been undone after a later step failed simply wasn't. The rollback ("saga") code existed and was unit-tested. On a real call, nothing rolled back, ever.
Root cause
Two independent bugs stacked. First: the API schema for a tool never declared an undo.url field, so pydantic silently dropped it on every save — every tool's undo URL was permanently blank, making rollback unreachable by anything a customer could configure. Second, deeper bug: the saga rolled back within one batch of tool calls. That assumes an LLM calls multiple tools together in one response. Groq's gpt-oss-120b — the model this deployment actually runs — doesn't batch. Asked for two things in one sentence, it called them as two separate batches of one, 1.5 seconds apart. No batch ever held both the success and the failure, so nothing ever qualified for rollback.
Why tests missed it
Unit tests constructed a batch containing both calls directly — a correct test of the rollback algorithm, but one that assumed a batching behaviour the real model in production never exhibits. The gap was between "the code is correct" and "the code's assumption about the model matches the actual model."
Fix
Declared undo.url in the schema. Rescoped the saga to accumulate across one caller request — reset on the frame that marks the caller has stopped speaking — rather than one batch, so it survives however many separate batches the model happens to split a request into.
commits 44cd0e9 · 192f382

A redirect reached the caller as "nothing was found"

TASK 3.6 · 2026-09-05
Symptom
A lookup tool hit against a real, renamed GitHub repository told the caller it didn't exist.
Root cause
GitHub answers a renamed repo with HTTP 301 and an empty body. The HTTP client used doesn't follow redirects by default; every field the tool was configured to extract resolved to None, and the code's own "everything came back empty" rule — built to catch APIs that return 200 with no real content — fired and reported the record as not found.
Fix
Deliberately not a blanket follow_redirects=True — that checks nothing, and a customer's own endpoint answering 302 → 169.254.169.254 (this server's own cloud metadata address) would have walked the server into fetching its own credentials. Each redirect hop is re-checked against the same SSRF allowlist as the original request, the auth header is dropped the moment the redirect crosses to a different host, and only GET/HEAD are followed — a redirected POST is refused rather than silently replayed, which could otherwise charge a payment twice.

Deployment & infrastructure

A reverse proxy fell through to the app's own HTML for three real API routes

DEPLOYMENT · 2026-09-07
Symptom
Caught before the affected features were even reached in testing: three backend routes — approvals, webhooks, payments — existed and worked, but nothing in the deployed reverse proxy config listed them.
Root cause
The proxy explicitly names which URL paths forward to the backend; everything else falls through to the single-page app's own HTML with HTTP 200. Three routers had been added to the backend across three different tasks, and the proxy config was never updated to match — each request for one of those paths returned a page of HTML with a 200 status, not an error.
Why tests missed it
The local dev server's proxy forwards anything it doesn't recognise itself to the backend by default — so all three routes worked perfectly on a laptop. Only the production proxy config had the gap, and nothing tests a deployed reverse-proxy config against the running application's actual route list.
Fix
Added the three missing routes to the proxy config. The one that mattered most: the payment provider's own webhook lands on one of those paths — a provider POSTing "payment received" would have received 200 and a page of HTML, marked the delivery successful, and never retried. A real payment, silently never recorded against the order, and the postmortem would have pointed at the payment provider instead of the proxy.
commit a36f7bc

The same deploy command reported success and changed nothing — twice

OPS · 2026-09-07
Symptom
Two unrelated incidents, hours apart, identical underneath. A rotated API key that the running service kept ignoring. Then a fixed reverse-proxy route that stayed broken after the fix was deployed. Both times the deploy command printed success.
Root cause
Bringing a service up compares the service definition — image, ports, declared environment — and does nothing if that is unchanged. Neither incident changed it. The first was a value inside an env file; the second was a config file mounted into the container. Both were correct on disk and neither was re-read, because from the orchestrator's point of view there was nothing to do.
Why it stayed hidden
The output says "Running" or "Started" where a real change says "Recreated" — one word, easy to read straight past, and no warning that the file you just edited is not the one in effect. It cost a round of "the fix didn't work" debugging on a fix that was correct both times.
Fix
Force a recreate for env changes, restart the service for a mounted config file, and — the part worth keeping — verify from inside the container rather than trusting the deploy: read the value back out of the running process's own environment, and make a real authenticated request through the same client the application uses. A convenience check gave a misleading answer here too: a bare HTTP client reported a 403 that had nothing to do with the credential, because the provider's edge network rejects unfamiliar user-agents.

A container kept serving a rotated credential after the file was fixed

OPS · 2026-09-07
Symptom
Rotated an LLM provider's API key after finding it exposed in a local permission config. Every call afterwards greeted the caller, then went silent — the greeting is TTS-only and worked; the actual conversation needs the LLM, which every request rejected with 401 invalid_api_key.
Root cause
The env file on disk had the new key. The running container did not — restarting a service with up -d reuses an existing container if its declared config hasn't changed, rather than reading the env file fresh. Confirmed directly: querying the key inside the running container returned the old prefix, not the new one.
Fix
--force-recreate on the container, then verified two ways before trusting it: reading the key's prefix back out of the container's actual environment, and making a real authenticated request through the exact SDK the application itself uses. Worth noting separately: a curl-based check gave a false 403 here — the provider sits behind an edge network that can reject a bare HTTP client's default user-agent — so the decisive check was reproducing the real call path, not the most convenient tool at hand.

Product gaps — correct backend, missing surface

A fully built, validated setting had no way to be set

TASK 3.5 · 2026-09-07
Symptom
The bot editor page had no timezone, opening-hours, or slot-length fields at all — not broken, simply absent.
Root cause
The backend had validated and stored all four fields since the booking feature was first built — schema, per-field validation (a real IANA zone, not a raw UTC offset that can't express daylight saving; HH:MM clocks), and the list endpoint already returned them. The frontend simply never grew the corresponding inputs. Every bot silently ran on the class defaults, with no way for an operator to say otherwise.
Fix
Added a Scheduling section to the editor: a time-zone dropdown (a closed list, not free text — the backend rejects anything the zone database can't resolve, so a text field would have mostly produced save errors), and opens/closes/slot-length inputs, wired straight to the endpoints that already existed.
commit efe91a0

An approval queue nobody could tell was full

TASK 3.10 · 2026-09-07
Symptom
A live call raised a refund approval correctly, held the action, and waited — and there was no way to know it had. The only signal was opening the Approvals page and looking.
Root cause
Every piece of the mechanism worked: the threshold check, the held action, the authenticated approve and deny, the queue itself. What was never built was the part that says something is waiting. The feature had been designed from the inside out — from what the system must guarantee — and never once from the position of the person who has to act within seconds while a caller holds the line. A test suite cannot catch this: nothing is wrong, there is simply nothing there.
Fix
A dedicated count endpoint (declared before the /{id} route, or the router would read “pending-count” as an approval id), and an amber badge on the Approvals link refreshed every twelve seconds. Amber rather than red: a waiting decision is a normal request, not a failure. The count also goes into the accessible label, because a screen reader announcing a bare “Approvals” loses the only part that says anything needs doing.
commit 7435757

Going to approve the refund hung up on the caller

TASK 3.10 · 2026-09-07
Symptom
Mid-call, pressing back to reach the Approvals page ended the call. The exact workflow task 3.10 exists for — approve a large refund while the caller waits on the line — could not be done in one browser tab.
Root cause
The call page owned the WebRTC peer connection, and its setup effect ended return () => stopSession(). React runs that on unmount, and a route change unmounts the page — so navigating and hanging up were literally the same action. Underneath that was a structural gap rather than a bug: App.tsx was thirty-eight lines of flat routes with the auth provider as the only wrapper, so nothing sat between the router and the pages, and nothing could outlive one. The same gap produced two quieter symptoms nobody had connected to it: the approvals badge could only ever appear on the dashboard, because that was the only page with any navigation on it; and every back button hardcoded a destination instead of stepping back through history, so back from Approvals went to the dashboard rather than to the call it came from.
Fix
Lifted the peer connection, microphone stream, audio element and data channel into a call context mounted above the routes; the call page became a view of that state rather than its owner, and nothing ends a call now except someone ending it. Added a layout route owning the background, header, navigation and badge, plus a call bar pinned to every other page while a call is live — bot name, timer, mute, end. Back became history-based with a per-page fallback. Net effect was mostly deletion: six hand-rolled headers, five copies of the background and six copies of the loading spinner went away.

Phase 4 — one symptom, three separate bugs

“The bot told me the wrong time” — and three different reasons why

PHASE 4 · 2026-09-12
Symptom
A caller asked for the date and time. The date was right; the time was 5.5 hours out. Fixed it — same wrong answer. Fixed it again — same wrong answer. The interesting part of this one isn’t any single bug, it’s that three unrelated faults produced an identical symptom, stacked, so each fix appeared to do nothing and looked like flailing.
Root cause — layer 1: the clock spoke UTC
get_current_datetime returned datetime.now(UTC) labelled “UTC”, knowing nothing about the bot’s configured zone. On the second call the model did something more revealing: it read the UTC time out and then remarked that “IST is UTC+5:30” — narrating the offset instead of applying it. A language model is not a calculation layer. Handing it a value in the wrong zone and hoping it converts is the same class of mistake as expecting it to enforce business hours.
Root cause — layer 2: the fix was unreachable
Layer 1’s fix changed nothing, because this bot never called that function. A bot with its own tools configured is given exactly those and every built-in is dropped — and this one had 8 tools, none of them a clock. One log line settled it: loaded 8 configured tool(s), and no tool call after it. With no clock to read, the model invented the time. Fixing what a function returns is wasted effort while nothing is calling it.
Root cause — layer 3: the model invented an argument
With the clock finally offered, the model called it as get_current_datetime(human_readable="2026-09-12 14:35:20 PDT") — inventing both the parameter and a US Pacific timestamp. The function takes no arguments, and the schema says so; the model had read the field name out of the docstring, which named it while describing what came back. The framework splats whatever arrives straight into the function with no filtering against the schema it generated moments earlier, so one invented key is a hard TypeError: the tool never runs and the model answers from imagination — the exact failure the tool exists to prevent.
Why tests missed it
Every test called the function directly, in Python, with correct arguments. Not one went through the path a real call uses — the framework generating a schema, a model choosing what to send, and that being splatted back in. The tests asserted the function was right, and it was; what was wrong was everything around it. Layer 2 had a test that actively encoded the bug: it asserted “configured means only configured”, which is precisely the rule that starved the bot of a clock.
Fix
Convert in code against the bot’s own zone, reusing the booking config so “what time is it” and “what time can I book” can never disagree. Offer exactly one built-in — the clock — to every bot regardless of configuration, on the grounds that knowing what day it is is ambient context, not a domain capability. And drop invented arguments instead of crashing on them, with a warning so a misbehaving model stays visible. The obvious version of that last fix was a trap: adding **kwargs to absorb it publishes a required argument called _ignored to the model — found by running it rather than reasoning about it, and now held shut by two tests.
before: arguments {'human_readable': '2026-09-12 14:35:20 PDT'} → TypeError, tool never ran after: arguments {} → "Saturday, 12 September 2026, 11:11 pm India time"
commits 8b56cdc · 3050be3 · d4ba16c

The logs that would have explained it were being thrown away

INFRASTRUCTURE · 2026-09-12
Symptom
Trying to diagnose the above from the container logs: 213 pipeline lines in the window, and not one tool line — on calls that demonstrably made tool calls. The evidence needed to find the bug simply wasn’t there, which is why the first two layers had to be diagnosed from what the caller heard.
Root cause
Python block-buffers its output when it isn’t writing to a terminal — which is exactly the case inside a container. Lines sit in that buffer until it fills or the process exits cleanly. Every call runs in its own worker process that is ended with terminate(), so a call’s last log lines weren’t delayed, they were discarded with the buffer. The lines that did survive were the ones written early enough in a long call to be pushed out by a later flush.
Why tests missed it
Nothing was broken for a caller, so nothing could fail. This is a class of defect a test suite cannot have an opinion about: the observability was broken, not the behaviour. It only becomes visible the day you need the logs and they aren’t there — which is the worst possible day to find out.
Fix
One line — PYTHONUNBUFFERED=1 in the container image — and a test asserting it stays there. Cheap, and it is what made the two remaining layers findable at all.
commit b848cbc

Total silence on the call — and it wasn’t the code

OPS · 2026-09-12
Symptom
Mid-debugging, the bot stopped being audible entirely. Connection fine, transcripts fine, speech recognised — nothing spoken back. Easy to assume a change had broken it.
Root cause
The text-to-speech provider had run out of credits and was returning quota_exceeded (HTTP 402) on every request. An external billing state, unrelated to any code change — but indistinguishable from a regression without reading the logs. Worth naming because the instinct under pressure is to revert recent work, which here would have thrown away good fixes and not restored audio.
Fix
Rotated the API key. Notable for the second lesson: an editing slip merged the new key onto the config file’s header comment, producing a file the container wouldn’t parse. Diagnosed with read-only commands, repaired by deleting the one bad line, and — the useful habit — validated with a config check before restarting anything, so a broken file was never handed to a running service.

Two regressions shipped because the test suite couldn’t run

PROCESS · 2026-09-12
Symptom
The database provider was blocking the development machine’s IP — a home connection whose address rotates — so pytest couldn’t reach it. Layer 2’s fix was verified by hand with a standalone script instead, and committed. The moment access was restored, the full suite found two tests that fix had broken.
Root cause
A manual script checks the thing you thought to check. A suite checks the things you didn’t — here, a test reading .name on every entry in the tool list, which broke the moment a plain function appeared alongside the objects, and a second test that encoded the old rule outright. Neither would have occurred to anyone to check by hand.
Fix
Permanent allowlist entry so a rotating home IP can never block the suite again — access still requires credentials, so the IP gate was providing very little. Then both regressions fixed for their own reasons rather than edited until green, and each attributed by rewinding the code and re-running to prove which commit caused it instead of assuming. The rule this leaves behind: if the suite cannot run, the commit is unverified — say so, and go back to it.
