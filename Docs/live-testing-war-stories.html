Phase 3 — booking & tool calling

A bot's timezone was configured correctly and spoken back wrong

TASK 3.5 · 2026-09-07
Symptom
Bot set to Asia/Kolkata, 09:00–18:00 in the UI. On a live call it offered appointment slots and spoke times in UTC — a 2pm booking would have confirmed as 7:30pm to an Indian caller. No error anywhere. The setting looked saved; it was silently ignored.
Root cause
Every phone call spawns its own OS process (one worker per call, so a crash on one call never touches another). That process registers, at startup, which database collections it's allowed to query — a fixed list passed to the ODM's init_db(). Bot had never been on that list, since the day per-call worker processes were introduced — nothing inside a call had ever needed to read a bot document directly; its config crosses into the process as a plain dict instead. The booking feature broke that assumption: it queries Bot.get(...) live, mid-call. That query raised CollectionWasNotInitialized on every single call — and its own try/except caught the error, logged a warning nobody was watching, and silently fell back to hardcoded defaults (UTC, 9–6, 30 min).
Why tests missed it
The test suite runs in a different process — the pytest runner — and that process's own init_db() registers the full model list, Bot included. So in tests, the exact same line of code succeeds, returns the real timezone, and the test correctly asserts correct behaviour. The test wasn't wrong — it was standing somewhere the bug structurally couldn't reach it.
Fix
Added Bot to the call worker's model list. Then wrote a structural regression test — not a behavioural one — that parses the source of every file that runs inside a call, finds every database model it queries, and asserts each is registered. Verified by literally reverting the fix and re-running: both new tests fail and name the exact file at fault.
before: "timezone": "UTC" (config said Asia/Kolkata) after: "timezone": "Asia/Kolkata" — no fallback warning logged

Rollback logic existed but could never fire

TASK 3.4 · 2026-09-05
Symptom
A tool call that should have been undone after a later step failed simply wasn't. The rollback ("saga") code existed and was unit-tested. On a real call, nothing rolled back, ever.
Root cause
Two independent bugs stacked. First: the API schema for a tool never declared an undo.url field, so pydantic silently dropped it on every save — every tool's undo URL was permanently blank, making rollback unreachable by anything a customer could configure. Second, deeper bug: the saga rolled back within one batch of tool calls. That assumes an LLM calls multiple tools together in one response. Groq's gpt-oss-120b — the model this deployment actually runs — doesn't batch. Asked for two things in one sentence, it called them as two separate batches of one, 1.5 seconds apart. No batch ever held both the success and the failure, so nothing ever qualified for rollback.
Why tests missed it
Unit tests constructed a batch containing both calls directly — a correct test of the rollback algorithm, but one that assumed a batching behaviour the real model in production never exhibits. The gap was between "the code is correct" and "the code's assumption about the model matches the actual model."
Fix
Declared undo.url in the schema. Rescoped the saga to accumulate across one caller request — reset on the frame that marks the caller has stopped speaking — rather than one batch, so it survives however many separate batches the model happens to split a request into.

A redirect reached the caller as "nothing was found"

TASK 3.6 · 2026-09-05
Symptom
A lookup tool hit against a real, renamed GitHub repository told the caller it didn't exist.
Root cause
GitHub answers a renamed repo with HTTP 301 and an empty body. The HTTP client used doesn't follow redirects by default; every field the tool was configured to extract resolved to None, and the code's own "everything came back empty" rule — built to catch APIs that return 200 with no real content — fired and reported the record as not found.
Fix
Deliberately not a blanket follow_redirects=True — that checks nothing, and a customer's own endpoint answering 302 → 169.254.169.254 (this server's own cloud metadata address) would have walked the server into fetching its own credentials. Each redirect hop is re-checked against the same SSRF allowlist as the original request, the auth header is dropped the moment the redirect crosses to a different host, and only GET/HEAD are followed — a redirected POST is refused rather than silently replayed, which could otherwise charge a payment twice.

02

Deployment & infrastructure

A reverse proxy fell through to the app's own HTML for three real API routes

DEPLOYMENT · 2026-09-07
Symptom
Caught before the affected features were even reached in testing: three backend routes — approvals, webhooks, payments — existed and worked, but nothing in the deployed reverse proxy config listed them.
Root cause
The proxy explicitly names which URL paths forward to the backend; everything else falls through to the single-page app's own HTML with HTTP 200. Three routers had been added to the backend across three different tasks, and the proxy config was never updated to match — each request for one of those paths returned a page of HTML with a 200 status, not an error.
Why tests missed it
The local dev server's proxy forwards anything it doesn't recognise itself to the backend by default — so all three routes worked perfectly on a laptop. Only the production proxy config had the gap, and nothing tests a deployed reverse-proxy config against the running application's actual route list.
Fix
Added the three missing routes to the proxy config. The one that mattered most: the payment provider's own webhook lands on one of those paths — a provider POSTing "payment received" would have received 200 and a page of HTML, marked the delivery successful, and never retried. A real payment, silently never recorded against the order, and the postmortem would have pointed at the payment provider instead of the proxy.

A container kept serving a rotated credential after the file was fixed

OPS · 2026-09-07
Symptom
Rotated an LLM provider's API key after finding it exposed in a local permission config. Every call afterwards greeted the caller, then went silent — the greeting is TTS-only and worked; the actual conversation needs the LLM, which every request rejected with 401 invalid_api_key.
Root cause
The env file on disk had the new key. The running container did not — restarting a service with up -d reuses an existing container if its declared config hasn't changed, rather than reading the env file fresh. Confirmed directly: querying the key inside the running container returned the old prefix, not the new one.
Fix
--force-recreate on the container, then verified two ways before trusting it: reading the key's prefix back out of the container's actual environment, and making a real authenticated request through the exact SDK the application itself uses. Worth noting separately: a curl-based check gave a false 403 here — the provider sits behind an edge network that can reject a bare HTTP client's default user-agent — so the decisive check was reproducing the real call path, not the most convenient tool at hand.

Product gaps — correct backend, missing surface

A fully built, validated setting had no way to be set

TASK 3.5 · 2026-09-07
Symptom
The bot editor page had no timezone, opening-hours, or slot-length fields at all — not broken, simply absent.
Root cause
The backend had validated and stored all four fields since the booking feature was first built — schema, per-field validation (a real IANA zone, not a raw UTC offset that can't express daylight saving; HH:MM clocks), and the list endpoint already returned them. The frontend simply never grew the corresponding inputs. Every bot silently ran on the class defaults, with no way for an operator to say otherwise.
Fix
Added a Scheduling section to the editor: a time-zone dropdown (a closed list, not free text — the backend rejects anything the zone database can't resolve, so a text field would have mostly produced save errors), and opens/closes/slot-length inputs, wired straight to the endpoints that already existed.
