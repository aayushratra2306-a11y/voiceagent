Voice Agent Revision Card

Ten minutes before the interview. One line per topic — the full reasoning lives in the Build Log.

A real-time voice agent that answers from a customer's own documents, does real work through configurable tools, and holds up under load. WebRTC in, Pipecat orchestrating speech → retrieval → language → speech, and every call in its own operating-system process so one crash cannot take the server down.

Phase 1 — Foundation quality

1.1Turn detection. Silero VAD hears speech; a separate Smart Turn ONNX model decides whether a pause means finished. VAD alone only hears silence.
1.2Groq for the LLM. LPU inference, not GPU. ~0.4s to first token — in speech, a second of delay is a silence people talk into.
1.3Function calling. JSON schemas, not prompt-parsed pseudo-tools. Makes intent structured data instead of text to guess at.
1.4Two real tools. Order lookup and appointment booking, proving the framework end to end.
1.5Transcripts. A pipeline processor, not logging bolted onto services — sees frames both directions, provider-independent.
1.6Query rewriting. A small fast model cleans the spoken transcript before embedding. Side effect: "page fifty" → "page 50", which deleted a hand-written number parser.
1.7Reranking. Cross-encoder over 20 candidates. Raw cosine clusters 0.60–0.65 for good and bad; reranked spreads 0.0–0.9. Spread is what makes a threshold possible.
1.8Hybrid search. Sparse keyword index alongside dense. They fail in different directions — reranking after the merge means the two scales never need reconciling.

Phase 2 — Swappable architecture

2.1Provider layer. Three factory functions. Deliberately thin — pipecat services already share base classes. Reused in Phase 4.8 to swap in free load-test stand-ins.
2.2Local speech. faster-whisper + Piper. Piper beat Kyutai Pocket TTS because Pocket has no Hindi voices. Both became the circuit-breaker fallback in 4.6.
2.3Self-hosted calls. GCP VM + Caddy + coturn. PaaS can't forward the UDP range TURN needs — the requirement dictates the infrastructure.
2.4Process per call. Crash containment + GIL. Two queues for IPC because the SDP answer must return live, which a config file can't do.
2.5Auth hardening. 15-min access, rotating httpOnly refresh, rate limit per-user then per-IP. Rotation makes theft detectable.
2.6Ownership + injection. One reusable dependency. Returns 404 not 403 so IDs can't be probed — a 403 is an information leak.
2.7Monitoring. Sentry ×2 (separate projects), Langfuse via plain OTLP — per-call cost. Phase 4.9 adds a second, non-overlapping system-level layer.
2.8Retrieval tests. 32 questions, 28 baseline, guard asserts a margin of 24 — a test that chases natural variance gets disabled.
2.9CI + protection. 5 jobs; 3 required. Retrieval excluded (paid calls), dependency audit excluded (continue-on-error, always green, protects nothing).
2.10Source citations. Over the WebRTC data channel; PDFs in GridFS so a citation opens at its page. Empty list renders as "general knowledge", not as missing data.

Phase 3 — Tasks and multi-tasking

3.1Tool plug-ins. Tools became database rows, not code. A generic HTTP tool with 4 auth modes covers most customer APIs with configuration alone.
3.2Parallel tools. Pipecat already runs them concurrently — no asyncio.gather needed. What was missing was per-tool timing visibility.
3.3Background jobs. Slow tools run async; the bot keeps talking and announces the result when it lands. In-flight jobs are never cancelled on hangup.
3.4Saga rollback. Undo scoped to one caller request, not one model "batch" — because Groq's model splits multi-step asks into separate batches, proven live.
3.5Booking template. The slot's own MongoDB _id is the lock — closes the double-booking race rather than narrowing it. UTC storage, spoken zone names.
3.6Lookup template. Dotted-path field mapping + call-scoped cache. A 301 redirect once read as "not found" — now followed under the same SSRF allowlist.
3.7Payment links. Sending is configuration through 3.1's tool; only the inbound HMAC-verified webhook is bespoke code. Never takes card numbers by voice.
3.8Webhooks. MongoDB outbox, not Redis — survives a restart, one fewer service. Signed outbound, mirroring 3.7's inbound check exactly.
3.9Bot templates. Plain code, not database seed data — ships and reviews like a feature. Applying one sets tools explicitly, not the unconfigured fallback.
3.10Human approval. Held, never rolled back — nothing to undo if it never ran. Shipped complete and still failed live: nobody could tell one was waiting until a badge was added.

Phase 4 — Scale foundations

4.1Rate limiting. Follows an optional REDIS_URL; stays in-memory until a second API replica actually exists. Not paid for today.
4.2Call queue. Real Redis Streams mechanism, built and tested, deliberately not wired in — /connect is synchronous, a queue only pays off with multi-machine workers.
4.3Worker autoscale. Grows on demand, shrinks after 4 quiet ticks. Found live: a still-starting worker looked like a full pool — 22s wait, zero autoscale signal — fixed by counting it as demand.
4.4DB pool sizing. Sized from the real worst case, verified against production Atlas: 18/500 normal, 88 worst case.
4.5Concurrency cap. Named slots in a Redis sorted set, not a bare counter — a bare counter would permanently burn capacity on every restart, since nothing releases it.
4.6Circuit breakers. Trip to a local backup, but only if it's actually installed. Proven live: held Cartesia's breaker open 3 minutes, a real call spoke in Piper's voice.
4.7Health + restarts. Two layers — plain Docker never restarts on an unhealthy label alone, proven directly on the server. A frozen loop can't watch itself.
4.8Free load test. The same provider factories swap in local stand-ins for zero-cost testing. Found the real ceiling: not memory, the warm pool's cold-start under a simultaneous burst.
4.9Monitoring. Self-hosted, localhost-only, email alerts. A test alert found the alerting itself silently broken — wrong file owner, permission denied, container reported healthy throughout.

Bugs — the mechanism in one line

fork vs spawn

Linux forks, Windows spawns. A forked child inherited an already-connected DB client bound to a dead event loop, so every write failed on the server only.

Sequel: the regression test for it was itself forking, and failed in CI months later.

Config that swallowed settings

Accepted unknown fields silently. Settings on the wrong object did nothing — no error, no warning. Bit four times across the project before it stopped being a one-off.

Unreachable TURN relay

coturn allocated relay sockets on Docker bridges. The browser got a candidate that looked correct, sent audio, and packets landed where nothing listened. Nothing logged an error.

The data channel nobody opened

The server only listens; it never creates one. After 10s it permanently disables the channel and discards every message. The browser had to call createDataChannel() before the offer.

A CI check that could never pass

Demanded 32/32; baseline is 28. Failed on every run since written. A check that can't pass teaches you that red is normal.

10GB of GPU libraries, no GPU

pip resolves torch to the CUDA build on Linux. Pinned by pip freeze on Windows, needed by nothing — Required-by was empty.

Monitoring pinned to a version that couldn't

OTLP ingestion only exists from v3. The config said v2. Labelled "unverified" — but it was checkable from docs the whole time.

The tempting insecure fix — twice

CI couldn't reach Atlas. Opening it to 0.0.0.0/0 would work instantly and expose production. Gave CI its own container instead — and that exact mistake happened for real later, from a local test run pointed at production by accident. The DB login is now permanently restricted so it can't drop a database at all.

Deploy said "Running", changed nothing

Bringing a container up compares only its definition. An edited env file or mounted config isn't re-read if nothing else changed. "Running" looks identical to "Recreated" unless you read closely.

Three days of fixes never reached the server

The build's own type-check failed on new test files. git pull && npm run build never installed the new dev dependency, so && stopped and the old bundle kept serving as if nothing happened.

One symptom, three stacked search failures

Wrong fragment searched, quota exhausted twice, then a 17s synchronous freeze. Each fix looked like it did nothing until the third one actually landed — "still broken" didn't mean "wrong fix".

The caller's own words were never saved

Pipecat's own aggregator consumes the frame the recorder was reading. Every transcript had the bot's reply and an empty string for the caller, since the feature shipped.

A backup voice never actually on the server

The download script had never been run there. The breaker tripped correctly and had nowhere to fail over to — proven only by running the real outage live, not by reading the code.

Alerting that was silently broken

Wrong file owner on the SMTP credential. The container started healthy, loaded its config, and every alert failed with "permission denied" — found only by sending a real test alert, not by reading the config.

If you remember only five things

Every call is its own OS process. Crash containment and GIL. It shapes the deployment, the tests, and several of the bugs — including one four phases later, in the same worker's own exit path.

Reranking, with the measurement. The correct chunk wasn't in the raw top five. Cosine clusters 0.60–0.65 for good and bad alike; reranked spreads 0.0–0.9, and that spread is what makes a threshold work.

"Still broken" doesn't mean "wrong fix". The page-50 search bug and the wrong-time bug each took three independent, stacked faults before they actually cleared — each fix was correct and each one looked like it had failed.

Proving beats reading the code. A written claim that Docker restarts an unhealthy container was false on the real platform. A circuit breaker with a fallback that was never actually installed tripped correctly and failed over to nothing. Both found only by testing the real thing, not the documentation of it.

Vendor decisions made cheap to reverse. Plain OTLP and a thin provider layer mean switching is config, not a rewrite — and that same layer later made a zero-cost load test possible with no changes to the real call path.
