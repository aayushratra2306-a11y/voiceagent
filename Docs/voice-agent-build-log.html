How to use this

Read once end to end; revisit the case files before an interview.

Every task below answers the same four questions, because those are the four an interviewer actually asks: why did you do it, how does it work, what else could you have used, and why this one.

The strongest section is Bugs, root-caused. Anyone can list tools they used. Explaining how you found a fault that only appears on Linux, or a check that could never pass, demonstrates that you actually built the thing. Spend your preparation time there.

A note on honesty. Where something is incomplete or was rejected, this document says so. "We chose Langfuse Cloud because self-hosting v3 needs 16 GB and our VM has 4" is a far better answer than pretending the decision was free. Interviewers probe for the trade-off; having it ready is the point.

The one architectural fact worth leading with: every call runs in its own operating-system process, not as a coroutine in a shared server. That single decision shapes the deployment, the tests, and several of the bugs below — including one four phases later, when the worker still wasn't exiting cleanly after the call ended.

Phase 1 — Foundation quality

Eight tasks making the conversation feel like a conversation, and the document search actually find things.

1.1

Smart turn detection and interruptions

Why

A bot that talks over you, or waits three seconds after you stop, is unusable regardless of how good its answers are. Turn-taking is the product in voice.

How

Silero VAD detects speech energy; a separate Smart Turn v3 ONNX model decides whether a pause means "finished" or "still thinking". VAD alone can't tell those apart — it only hears silence.

Options

Fixed silence timeout (simplest, always wrong for someone who pauses mid-sentence); VAD only; a cloud turn-detection service (latency and cost per call).

Why this

The Smart Turn model runs locally on CPU via ONNX — no network hop in the most latency-sensitive path in the system. It ships inside pipecat, so there was no model to host.

1.2

Move the language model to Groq

Why

In text chat, a second of latency is invisible. In speech it is a silence the caller notices and starts talking into.

How

GroqLLMService running openai/gpt-oss-120b, with reasoning_effort=low to stop the model thinking longer than the conversation can tolerate.

Options

OpenAI GPT-4o (kept as fallback), Anthropic, self-hosted Llama on a GPU.

Why this

Groq runs on LPUs rather than GPUs and returns first tokens markedly faster at comparable quality. Measured time-to-first-byte in production sits around 0.39–0.44 s. Self-hosting would have meant a GPU instance the project doesn't have and doesn't need.

1.3–1.4

Function calling, and two real tools

Why

A bot that can only talk is a demo. A bot that can look up an order or book an appointment is a product.

How

Tools are declared as JSON schemas and registered with the LLM service; pipecat auto-registers the handlers. Three exist: get_current_datetime, get_order_status, book_appointment.

Options

Prompt-engineered pseudo-tools parsed out of the reply text — brittle, and fails silently when the model phrases things differently.

Why this

Native function calling makes the model's intent structured data rather than text to be guessed at. Phase 3 turns this into a configuration-driven plug-in system, which only works because the foundation is structured.

1.5

Save conversation transcripts

Why

Without transcripts you cannot debug a complaint, measure quality, or show a customer what their bot said.

How

A TranscriptRecorder frame processor sits in the pipeline and writes a ConversationTurn per exchange, carrying per-stage timings — time to first token, time to speech.

Why this

Implemented as a pipeline processor rather than logging bolted onto the service classes, so it sees frames flowing in both directions and stays independent of which provider is in use.

1.6

Rewrite spoken questions before searching

Why

People speak in false starts. "Um, can you tell me, uh, what's on page fifty?" embeds badly — the filler words carry as much vector weight as the real question.

How

A small fast model (gpt-oss-20b, deliberately not the conversational one) rewrites the transcript into a clean search query before it is embedded. It falls back to the raw query on any failure.

Why this

It sits directly in the latency path of every lookup, so model size matters more than model quality here. It also replaced a hand-written number-word parser: the rewriter turns "page fifty" into "page 50" as a side effect, so the page-extraction regex now only handles digits. A whole class of parsing code deleted.

1.7

Rerank the search results

Why

This is the most quantified decision in the build. For the query "what avoids mistakes when using claude code", the genuinely correct chunk — page 40 — did not appear in the raw top five at all.

How

Retrieve a wide pool of 20 candidates on raw vector similarity, then pass query and candidates together to a cross-encoder (bge-reranker-v2-m3, hosted by Pinecone) which reads them as a pair and scores real relevance. Keep what clears the threshold.

Why this

The measurement tells the whole story. Raw cosine scores cluster tightly — 0.60 to 0.65 for good and irrelevant matches alike — so no threshold can separate them. Reranked scores spread out: 0.0 for genuinely unrelated, 0.4–0.9 for real matches. The correct page 40 chunk ranked first at 0.9047, with clear air to the next at 0.7582. Spread is what makes a threshold possible at all.

1.8

Add keyword search alongside meaning search

Why

Dense vectors are excellent at meaning and poor at exact tokens. Ask for a specific product code or an unusual proper noun and semantic search drifts to things that are merely about the same topic.

How

A second sparse (keyword) Pinecone index runs alongside the dense one. Results merge, deduplicate by id, and the combined pool goes to the reranker.

Why this

The two methods fail in different directions, which is exactly when combining helps. Reranking after the merge means the two score scales never have to be reconciled — the cross-encoder rescores everything on one scale of its own.

Phase 2 — Swappable architecture

Ten tasks turning a working prototype into something that can be deployed, operated, and trusted.

2.1

The provider switching layer

Why

Being locked to one speech vendor is a commercial risk as much as a technical one — the day their pricing changes or a customer demands on-premise, you rewrite the pipeline.

How

Three factory functions in providers.py. The pipeline calls those instead of constructing services directly, so switching cloud to local is one settings value.

Why this

Deliberately thin. Pipecat's services already share base classes, so this is plumbing, not a new abstraction. The failure mode to name in an interview: provider-specific special cases creeping into the callers rather than the factories — that is exactly how this kind of layer quietly stops working. It paid for itself again in Phase 4.8: a fourth branch in the same three factories swaps in local stand-in services for a free load test, at no cost to the real code paths.

2.2

Local speech recognition and voice

Why

Two reasons, and the second is the one that mattered. Data residency for enterprise customers — and being blocked mid-development when a free tier runs out, which happened with Cartesia credits.

How

faster-whisper for recognition, Piper for speech. Both verified with real audio, including Hindi.

Options

OpenAI Whisper (reference implementation, needs PyTorch); Kyutai Pocket TTS; Coqui.

Why this

Piper beat Kyutai Pocket TTS on one disqualifying fact: Pocket has no Hindi voices, and this bot is bilingual. A capability gap beats a quality comparison. faster-whisper runs on CTranslate2 rather than PyTorch — which later turned out to matter a great deal (see the torch case file). Both became load-bearing again in Phase 4.6, as the circuit breaker's local fallback when the cloud providers trip.

2.3

Self-host the call connection server

Why

WebRTC needs UDP and a TURN relay. Roughly one connection in five — symmetric NAT, corporate firewalls, many mobile carriers — cannot connect peer-to-peer at all and must be relayed.

How

A GCP e2-medium running Docker Compose: the backend, Caddy for automatic HTTPS, and coturn as the TURN relay. The browser fetches ICE configuration from the server rather than hardcoding it.

Options

Render, Railway, Vercel; a managed TURN service such as Twilio.

Why this

Platform-as-a-service hosts terminate HTTP and do not forward arbitrary UDP port ranges, so TURN cannot run on them at all. This is a case where the requirement dictates the infrastructure. Deploying found three real bugs that no amount of local testing would have.

2.4

One operating-system process per call

Why

Every call ran as an asyncio task in one uvicorn process. A native fault in onnxruntime or CTranslate2 — both in the local speech path — would take down the server and every other live call with it. Simultaneous calls also competed for one GIL.

How

Each call gets its own multiprocessing.Process, spawned at connect and torn down at hangup, with two queues for inter-process communication: one carrying the WebRTC answer back to the parent, one carrying trickled ICE candidates forward. Phase 4 added a pre-warmed pool of idle workers that autoscales, so the caller claims one already running rather than waiting for a cold start.

Options

Passing configuration by environment variable or a config file; threads instead of processes.

Why this

Queues rather than a file because the WebRTC handshake needs the SDP answer handed back live — a one-shot file cannot do that. Processes rather than threads because the GIL makes threads pointless for CPU-bound audio work, and a thread cannot contain a native crash. This decision resurfaced twice more in Phase 4: once when a database model wasn't registered inside the worker process (see the case files), and once when a worker's own cleanup threads turned out to block process exit, silently leaking capacity.

2.5

Harden login security

Why

A stolen 60-minute token is valid for 60 minutes and cannot be cancelled. That is not acceptable once real customer conversations are behind it.

How

Access tokens live 15 minutes. A revocable refresh token sits in an httpOnly cookie and rotates on every use. The frontend refreshes transparently on a 401, with a single in-flight refresh shared across concurrent requests. Rate limiting is per-user where a token exists, per-IP otherwise.

Why this

Three details worth being able to defend. httpOnly means JavaScript cannot read the refresh token, so an XSS flaw cannot steal it. Rotation on use means a stolen token stops working the moment the real user refreshes — theft becomes detectable. Per-user before per-IP because IP-only limiting punishes everyone in a shared office along with the one person misbehaving. The revocation list is MongoDB rather than Redis simply because no Redis was deployed; functionally equivalent at this scale.

2.6

Ownership checks and prompt-injection defence

Why

The risk was never that a written check was wrong. It was that a new route would ship without one.

How

One reusable FastAPI dependency per owned resource replaces the repeated inline checks. A route either declares it and is safe, or obviously does not. Plus a prompt-injection blocklist and a length cap on bot instructions. Thirteen tests cover cross-user isolation and prompt validation.

Why this

The detail interviewers like: it returns 404, not 403, for both "does not exist" and "exists but is not yours". Identical responses mean an attacker cannot probe IDs to learn which ones are real. A 403 is an information leak dressed up as good manners.

2.7

Error tracking and AI monitoring

Why

When the bot broke for someone at 2am nobody found out. And with no cost-per-conversation figure, pricing the product later would be guesswork.

How

Sentry on backend and browser as separate projects. Pipecat already emits OpenTelemetry spans per stage; Langfuse ingests OTLP, so tracing is an exporter and credentials rather than hand-instrumentation. An error-spike monitor fires above 20 errors per hour.

Options

Self-hosted Langfuse v3; Arize Phoenix; deferring the whole thing.

Why this

Two rejections worth explaining, both in the case files below. Self-hosting needs 16 GB against a 4 GB VM. Phoenix is one container instead of six but cannot parse the gen_ai.* attributes pipecat emits, so traces would arrive with no model, tokens or cost. Separate Sentry projects because mixing a browser and a Python service breaks per-platform issue grouping. Phase 4.9 added a second, deliberately non-overlapping monitoring layer on top — see that task for why per-call cost tracing and system-level dashboards are not the same job.

The honest gap

Speech-to-text and text-to-speech bill per audio-second and per character, not tokens, so they arrive under metrics.* and Langfuse records the usage without pricing it. Language-model cost is exact; the audio legs need their own rates applied. Real calls measure at $0.0003–$0.0006 each.

2.8

A test suite for document search

Why

Search settings were being tuned by feel, which means you genuinely cannot tell whether a change helped or quietly broke something else.

How

Thirty-two questions with known correct pages, run through the real retrieval path. Baseline 28/32.

Why this

The regression guard asserts a margin (24/32), not the exact baseline. Retrieval has genuine day-to-day variance — model updates, index state — and a test that chases every point of natural fluctuation gets disabled within a week. The four known misses are understood: two land on a page adjacent to the right one, two paraphrases score under threshold.

2.9

Automated testing and branch protection

Why

Catch a break before it merges, and a leaked key before it reaches a public repository.

How

Five GitHub Actions jobs — lint, tests, dependency audit, secret scan, retrieval quality. main requires a pull request and three passing checks.

Why this

Two deliberate exclusions from the required set. Retrieval quality is excluded because it makes real paid API calls and one network hiccup would block an unrelated merge. Dependency audit is excluded because it runs with continue-on-error, so it always reports success and would protect nothing. Required approvals are set to zero — with a single developer, requiring one makes main permanently unmergeable.

2.10

Show which document an answer came from

Why

"The AI said so" is not something a business customer will accept. Showing the source turns a black box into something auditable.

How

Retrieval returns citations alongside the text — one entry per document and page, deduplicated, best first. The backend publishes them over the WebRTC data channel. Original PDFs are kept in GridFS so a citation opens at the page it came from.

Why this

Three defensible details. Citations are keyed by chunk text internally because the reranker returns documents by text and discards the ids sent to it. The score is deliberately null on the fallback path — raw cosine sits on a different scale and showing one beside a reranked score would misrepresent confidence. And an empty source list renders as "General knowledge — not from your documents" rather than as missing data, because being able to see that distinction is most of the feature's value.

Storage choice

GridFS rather than a document field, because MongoDB caps a document at 16 MB. GridFS rather than local disk, because the backend runs one process per call inside a container — a file on local disk is invisible to other workers and gone on the next deploy.

Phase 3 — Tasks and multi-tasking

Ten tasks turning the bot from something that talks into something that does work. Every task here was verified on a real call, and six of the corrections below came directly from that testing.

3.1

The tool plug-in system

Why

Every customer wants different tools. If each one needs code written and deployed, the business never scales past a handful of customers.

How

A bot's tools became rows in MongoDB (BotTool) rather than Python functions. A generic HTTP tool can call almost any REST API — method, headers, query and body all templated from what the model supplied — with four authentication modes (bearer token, custom header, query parameter, username/password). The FunctionSchema pipecat hands the model is built at call time from the database row, with the handler closure attached to it.

Options

A fixed plugin registry, each integration its own code module and deploy.

Why this

The plan called for a plug-in registry; what actually decides whether a new customer integration is a form or a development project is the generic HTTP tool sitting inside it. A bot with nothing configured falls back to every built-in tool, which matters for the bots nobody has configured yet.

3.2

Running several tools at once

Why

"Book the cab and text me the receipt" run one after another doubles the wait, and in a voice conversation that delay is very noticeable.

How

No asyncio.gather was written. Pipecat already runs a turn's tool calls concurrently on its own; the actual gap was visibility — a per-tool timer that logs how long each call took and how many ran together.

Why this

Adding a second scheduler on top of pipecat's own would have been more code for the same behaviour, with new failure modes of its own. The genuinely missing piece was being able to see a slow tool by name instead of "the bot felt slow" — and that visibility caught the partial-failure case directly: one call succeeding and one failing in the same turn is the normal case at volume, and the model needs telling explicitly, or it summarises both as done.

3.3

Slow jobs run in the background

Why

Some real APIs take five or ten seconds. Silence that long on a phone call is unbearable, and callers hang up.

How

asyncio.create_task starts the job; the bot says it is working on it and keeps talking. When the job finishes, an LLMMessagesAppendFrame drops the result into the conversation and asks the model to respond — so the bot phrases the news itself, not a canned sentence. Only tools marked long_running get this treatment.

Why this

A job already in flight is deliberately not cancelled when the caller hangs up. Cancelling a request that may already have booked something makes the other system's state genuinely unknowable, so it is allowed to finish and the outcome is logged loudly — that log line is the only record anybody has that it happened.

3.4

Undoing earlier steps when a later one fails

Why

"Book the cab and text me the receipt" is one request. If the receipt fails, the caller should not be left paying for half a job.

How

A saga: each tool optionally declares how to undo itself. Every completed step in a workflow is recorded as it happens; on failure, the recorded steps are walked backwards, running each undo.

Why this — and the correction that mattered

The unit of work was originally one batch of tool calls issued together in a single model response — and a real call on 5 September proved the model this project runs never issues them that way. Asked to book a slot and send a receipt in one breath, the model called book_slot, read the answer, then called send_receipt 1.5 seconds later as a second, separate batch of one. No batch ever held both the success and the failure, so nothing ever qualified for rollback. Rescoped to accumulate across one caller request instead — reset on the frame marking the caller stopped speaking — so it survives however many batches the model happens to split a request into.

3.5

The booking tool template

Why

Booking is the single most requested capability across almost every industry. A solid template turns most new customers into configuration rather than development.

How

Slots live in MongoDB, and the slot's own _id is the lock: two callers told 3 PM is free both try to book it, and MongoDB refuses the second insert outright. Times are stored in UTC and converted with zoneinfo for display and speech, which always names the zone — "three PM India time", never a bare "three PM".

Why this — and two live corrections

No external calendar API: the hard part of booking was never storing an event, it was two callers claiming the same slot at the same instant, and the unique-id insert closes that gap completely rather than merely narrowing it. Live testing then found two real gaps: the timezone and hours settings existed in the database with no screen to set them, and opening hours were offered to the caller but never actually enforced against a direct request — a caller could push past the offered times and book 2 AM. Both fixed; see the case files.

3.6

The lookup tool template

Why

"Where is my order" is the most common support question there is. A reusable template turns each new customer into a configuration exercise.

How

Built on 3.1's generic HTTP tool, with dotted-path field mapping (data.order.status) so it can point at whatever shape a customer's API actually returns, plus a call-scoped cache — asking the same thing twice in one call never repeats the request, and it dies with the call so nothing stale can leak into the next one.

Why this — and a live correction

A real GitHub repository that had been renamed answered with an HTTP 301 and an empty body. The tool didn't follow redirects by default, every mapped field came back empty, and the existing "everything is empty" rule — built to catch a 200 with no real content — reported the record as not found. Fixed deliberately not with a blanket follow_redirects=True: each hop is now re-checked against the same SSRF allowlist as the original request, the auth header is dropped the moment a redirect crosses to a different host, and only GET/HEAD are followed, so a redirected POST is refused rather than silently replayed — which could otherwise charge a payment twice.

3.7

The payment link tool

Why

Turning a conversation into a collected payment is the clearest return on investment a customer can be shown, and the easiest thing to justify paying for.

How

Sending the link is configuration through 3.1's generic HTTP tool — no provider-specific code needed there. The only code written is the inbound webhook: HMAC-SHA256 with compare_digest verifies a payment callback actually came from the provider, and a PaymentSession record ties the reference back to the call, recorded whether or not anyone is still listening; announcing it into a live call is best-effort on top.

Why this

Razorpay's own account was still behind identity checks at test time, so the live test ran against a stub echoing back whatever it was sent — which turned out to be the stronger test: it let a forged signature be sent, something a real provider can never produce, and confirming that gets rejected is exactly the check that stops a stranger telling a caller their money went through. Never taking card numbers by voice was a fixed rule from the start; the compliance burden of handling card data directly is enormous and entirely avoidable by always sending a link instead.

3.8

The webhook system

Why

Customers want events flowing into their own tools without a bespoke integration for each one.

How

An outbox in MongoDB, not Redis — the notification is written first and a separate loop sends it, so a process restart mid-send never loses the event. Every outbound request is signed with HMAC-SHA256, the exact mirror of 3.7's inbound check, and retried with increasing delays. Every attempt, successful or not, is kept in a delivery log.

Why this

No Redis: the queue lives in the database that is already running, which is one fewer service to operate, back up and pay for, and it survives a restart the same way a database record does. Signing every webhook is not optional — without a signature, the receiving system cannot tell a real notification from a forged one, and any competent customer will refuse to accept unsigned events at all.

3.9

Bot starting templates

Why

A blank instruction box is intimidating and produces bad bots. Templates dramatically shorten the time from signing up to seeing something impressive.

How

Plain Python data, not database seed rows — templates are content that ships with the product, not a customer's own data, so they change through a code review rather than a migration. A React picker offers them; applying one also creates the matching tool rows explicitly, one row per named tool.

Why this

The fallback for an unconfigured bot is every built-in tool — and a tutoring bot offered an appointment booker is exactly the irrelevance templates exist to avoid, so applying a template has to set tools explicitly rather than leaving the fallback in place.

3.10

Human approval for high-value actions

Why

No company will let an AI approve a large refund unsupervised. Having a gate is what makes them comfortable letting it handle everything below the threshold — which is where the call volume actually is.

How

A PendingApproval record per tool crossing its configured threshold, held before the action is sent — not undone afterwards, held. Authenticated approve and deny, and a count endpoint feeding an amber badge in the app header, polled every twelve seconds.

Why this — and a live correction

Held, not rolled back, is deliberately stronger than any undo: there is nothing to reverse if the action never ran. The mechanism shipped complete — threshold check, held action, authenticated decision, queue — and still failed its own purpose on a real call: nothing told anyone something was waiting except opening the Approvals page and looking. The whole thing had been designed from what the system must guarantee, never once from the position of a person who has seconds to act while a caller holds the line. Fixed with the badge; amber rather than red, because a waiting decision is a normal request, not a failure.

Phase 4 — Scale foundations

Nine tasks for handling many calls at once instead of one at a time, and for finding out — honestly, and at no cost where possible — where the real ceiling actually is.

4.1

Rate limiting that survives more than one replica

Why

An in-memory rate limiter only knows about requests that hit the same process. The moment there is more than one API replica, each one enforces its own separate limit and the real ceiling is never what it claims to be.

How

The limiter now follows a REDIS_URL setting: unset, it keeps the exact pre-Phase-4 in-memory behaviour; set, it shares counts through Redis. A self-hosted Redis container exists in the compose file, inert until that variable is actually filled in.

Why this

Deliberately optional rather than switched on outright. This deployment is a single VM with one API process, so Redis-backed limiting buys nothing yet and only earns its keep the day a second replica exists. Turning it on today would be paying an operational cost — another service to run, back up and watch — for a problem this deployment does not have.

4.2

The call queue and worker pool mechanism

Why

Accepting a call and having capacity to run it are two different things. A queue decouples them, so a spike waits politely on a queue rather than collapsing everything at once.

How

A real Redis Streams consumer-group mechanism — claim-once semantics, dead-worker recovery via XAUTOCLAIM — built and proven against a fake Redis in tests.

Why this — and why it is deliberately not wired in

The one honest gap in Phase 4, stated plainly rather than glossed over: POST /connect does a synchronous WebRTC handshake — the SDP answer is the HTTP response — so a queue only pays off once workers can run on a different machine from the one that accepted the call. That needs either an asynchronous signalling flow (the browser polling for an answer instead of getting one inline, a client-side change) or a second machine to route work to, and this deployment has neither. Wiring the mechanism in now would move four multiprocessing channels and the live-call registry onto Redis for no operational benefit — an architecture decision, not a coding task, deliberately left for the day multi-machine workers are actually needed.

4.3

The worker pool grows and shrinks with demand

Why

A fixed number of warm workers is either wasted memory overnight or a cold-start tax at the worst possible moment. Following real demand avoids both.

How

The pool grows on a cold-spawn demand signal if free memory allows, and shrinks by one after four consecutive quiet ticks — a step function, not a sudden collapse. call_worker_pool_min/max bound it.

Why this — and a live correction

The scaling decision itself was a clean, well-tested pure function: given "exhausted", grow. What it was fed was wrong. The only demand signal was the idle-worker list being empty — but a claimed worker is replaced immediately, and the replacement enters the list the moment its process starts, about eight seconds before it can actually take a call. Under a real burst the list is almost never empty, so callers were handed a still-starting worker, sat through the exact cold start the pool exists to prevent, and the autoscaler reported a perfectly healthy pool throughout — measured live at a 22-second wait with zero autoscale signal. Fixed by counting a still-starting claim as demand too, the same as an empty pool.

4.4

Sizing database connections for the worst case

Why

Every call-handling process opening its own connections can exhaust the database's connection limit outright, and the failure mode is every call failing at once, not gracefully.

How

Motor's pool is sized per-process — task 2.4 means one process serves at most one call — from the real worst case: warm pool at its maximum, every slot holding a live call, each opening its own small pool.

Why this

Verified against the real production cluster rather than assumed: 18 of 500 available connections in normal use, 88 in the calculated worst case — comfortable headroom on Atlas's free-tier ceiline without needing to touch it. Read-replica routing exists in the code but stays off until an actual replica is provisioned; reading from a replica that lags behind a very recent write is a genuinely confusing bug to chase, and there is no replica yet to make that trade worthwhile.

4.5

Capping simultaneous calls

Why

Without a ceiling, a spike degrades every live call at once. With one, existing calls stay perfect and new ones are refused cleanly instead.

How

A Redis sorted set of named slots, not a bare counter — checked and claimed atomically before the database lookup in connect(), ahead of any other work a new call would otherwise start. max_concurrent_calls defaults to 6, sized from real load-test numbers.

Why this — and why named slots, not a counter

A bare Redis INCR/DECR has no memory of which calls hold a slot, so a process restart mid-call — exactly what task 4.7's watchdog does on purpose — would have permanently burned that call's capacity with nothing to release it. Named members in a sorted set let a node clear its own leftovers at boot, plus a TTL sweep as a backstop for a node that never comes back at all. The capacity check running before the database lookup was a deliberate, test-encoded decision — reversed once, then reinstated after review, and the trade is recorded rather than hidden: a call over capacity is refused before spending a database round trip on a caller who is going to be turned away regardless.

4.6

Circuit breakers on external providers

Why

A slow provider is worse than a dead one. Without protection, every call waits out the same timeout at once and the whole system freezes together.

How

A SQLite-backed breaker (shared state across every per-call process, task 2.4's own architecture made this free) wired into two places: the customer-configured HTTP tool caller, per host, and the cloud voice providers via a pipeline observer. A tripped provider breaker switches to the matching local backup from task 2.2 — but only if that backup's model files are actually installed on the machine; downloading several hundred megabytes mid-call would be worse than the outage it's meant to fix.

Why this — and a two-layer live correction

Proven the way the task demands: the provider was broken on purpose, held open for three minutes, and a real call was built on the backup and spoke in its voice with no key changed and no restart. Getting there took two real fixes first. The refusal-guard logic was right and the model files were simply never installed on the server — the download script had never been run there. Installing them revealed a second gap: the speech-recognition backup landed in a machine-learning library's default cache, inside the container's own filesystem, which the very next routine rebuild would have deleted — quietly returning to "not ready" until the next real outage found out. Fixed by pointing that cache into the same persistent volume as the rest of the local models.

4.7

Health checks and automatic restarts

Why

Processes get stuck. Without detection, a frozen worker silently stops taking calls and the first sign of it is a complaint.

How

Two layers, deliberately not one. An in-process watchdog restarts after three consecutive unhealthy readings — and defers while real calls are in progress, bounded so a genuinely wedged process still recovers. Docker's own HEALTHCHECK covers the case the watchdog structurally cannot: a probe forces the app to answer within 5 seconds and the healthcheck itself waits 8; after 3 checks in a row with no answer at all, it force-stops the app process (init: true in the compose file, because the kernel ignores a kill sent to a namespace's own pid 1) and the restart policy brings it back.

Why this — and a live correction

A written claim that a frozen app was "covered by the container's health check, and Docker restarting on repeated failure" turned out to be false on the actual platform: plain Docker, without Swarm or Kubernetes, never restarts a container for being unhealthy — it only sets a label. Proven directly on the production server with two throwaway containers: one alive but failing its check sat at restarts=0 after 40 seconds; one that actually exited restarted four times. The first version of the force-stop fix had its own trap, caught by independent review before it shipped: its timeout equalled the database ping's own timeout, so a genuinely working app suffering a real database outage would have answered honestly with a 503 that arrived as "no answer at all" and been killed mid-call. Fixed by bounding every health reading to well under the probe's own window.

4.8

Load testing the system

Why

Capacity you have never tested is capacity you cannot honestly claim. A real number, found before a customer does, is the whole point of the task.

How

A real aiortc-based harness that mirrors the frontend's own connect flow — a genuine WebRTC handshake per simulated call, not a synthetic request. It ramps through concurrency steps, measures connect latency, ICE-connected time and time to first audible bot frame, and stops itself the moment a step has a call that fails to connect.

Why this — and the free path that made it possible at all

Real Deepgram/Groq/Cartesia traffic hits Groq's free-tier limit at roughly two simultaneous callers — nowhere near this server's own ceiling. A rehearsal mode (one setting, STANDIN_PROVIDERS) swaps the same three provider factories from task 2.1 to local stand-in services and switches off the knowledge-base lookup, so the exact same harness can run a real concurrency ramp against the real server for zero cost, as many times as needed. The ramp found the real ceiling directly: 1, 2 and 3 simultaneous calls all connected and answered cleanly; at 5, three calls needing a cold-started worker at the same moment — competing for two vCPUs to import the whole pipecat stack — took over a minute, past the point any caller would wait. The server's memory was never the constraint; the warm-worker pool's cold-start behaviour under a simultaneous burst was.

4.9

Monitoring dashboards

Why

You cannot fix what you cannot see, and an alert that never reaches anyone is the same as no alert at all.

How

Self-hosted Prometheus, Grafana and Alertmanager, all bound to 127.0.0.1 only — reachable by SSH tunnel, never the public internet. A bearer token protects the /metrics scrape itself, since it names which customer APIs have tripped a breaker and how many calls are live. Alertmanager routes firing rules to email, with grouping and a repeat interval so a flapping problem cannot fill an inbox.

Why this — and two things proven, not assumed

System-level numbers only — live calls, warm-pool size, breaker state, database sizing — deliberately not duplicating task 2.7's Langfuse, which already owns per-call cost and latency from inside each call's own process; the two cover different halves on purpose. Two gaps were found and closed only by actually testing the chain rather than trusting the config. First: a provider breaker only gets a row in its store once it has misbehaved, so a freshly started container exported no provider breakers at all and the dashboard panel read "No data" — indistinguishable from a broken exporter, the same ambiguity the health endpoint's own breaker_store field exists to remove elsewhere. Fixed by seeding the known providers closed before the real snapshot overlays them, verified by deliberately reversing the seeding order and confirming the regression test catches it. Second, and worse: a synthetic test alert sent through the real chain failed silently — the Alertmanager container started, loaded its config and reported perfectly healthy, while every send failed with a permission error, because it runs as a different user than the one that created the credential file. The one thing meant to say "something is broken" was the thing that was broken, and only sending a real alert — not reading the config — surfaced it.

Bugs, root-caused

The strongest interview material here. Each one is a specific mechanism, not a vague "we had some issues".

Silent

A config object that silently swallowed settings

Symptom

Voice activity detection tuning appeared to have no effect. Later, audio configuration on the same object also did nothing.

Cause

PipelineParams accepts arbitrary keyword arguments and discards ones it does not recognise. The fields belonged on TransportParams. No error, no warning — the code read perfectly and did nothing.

How it was found

Reading the installed library source rather than the documentation, and confirming with hasattr() on a constructed instance. It bit twice, which is the interesting part: the same silent-drop pattern in the same class, months apart. It bit a third and fourth time later — Deepgram's language/endpointing settings and Cartesia's voice/language both being passed as bare constructor kwargs instead of the documented settings= object, discovered while chasing a Hindi caller being transcribed and spoken back to entirely in English.

Lesson

A library that accepts unknown fields without complaint will let you write confident code that has no effect. When a setting appears not to work, verify the field exists before assuming the value is wrong — and after the third occurrence of the same pattern in one codebase, it stops being a one-off and starts being a thing to check for by default.

Platform

fork versus spawn — every database write failing on Linux

Symptom

Worked perfectly on Windows. On the deployed Linux server, every database write inside a call failed silently — transcripts, order lookups, bookings.

Cause

multiprocessing defaults to spawn on Windows and fork on Linux. A spawned child is a fresh interpreter that re-imports and re-initialises everything. A forked child inherits the parent's memory — including an already-connected Mongo client bound to an event loop that does not exist in the child.

Fix

Force spawn on every platform, and have the worker call database initialisation itself rather than assuming it inherited it.

The sequel

Months later CI failed on the one test written to prove this fix. The test had been left on the platform default — so on Linux it forked, and was exercising a code path production never takes. The regression test for a fork bug was itself forking. Pinning the test's context to spawn fixed it. A related, later gap in the same area: a worker's own database model list simply never included Bot, because nothing had ever needed to read a bot document mid-call until the booking feature did — every call silently fell back to hardcoded defaults, caught only by a structural test that parses every file that runs inside a call and asserts every model it queries is registered.

Network

A TURN relay handing out addresses nobody could reach

Symptom

Calls from restrictive networks failed. ICE went from checking straight to disconnected. No error appeared in any log.

Cause

With no relay address pinned, coturn auto-discovered every local interface and allocated relay sockets on Docker's bridge networks as well as the real one. A bare external-IP flag then labelled all of them with the public address. The browser received a relay candidate that looked perfectly correct, sent audio to it, and the packets arrived on an interface where nothing was listening.

Fix

Pin the relay address to the real network interface and use the public/private form of the external-IP flag so coturn knows which local address the public one maps to.

Lesson

The hardest faults are the ones where every component reports success. Nothing here logged an error — the audio simply went somewhere real and was ignored.

Protocol

A data channel that nobody opened

Symptom

Source citations never reached the browser. The backend logged Data channel not ready, queuing message indefinitely.

Cause

Reading pipecat's transport source showed the server only ever listens for a data channel — it never creates one. After a ten-second timeout it permanently disables the channel and silently discards every message. The browser had never called createDataChannel().

Fix

Create the channel in the browser before generating the offer, so it lands in the SDP.

Lesson

In a client/server protocol, "who initiates" is a real design decision and is often documented nowhere. The log line had been sitting in production for days looking like an unimportant warning.

Async

Awaiting something that was never asynchronous

Symptom

A warning logged on every single conversational turn, even though the feature worked.

Cause

send_app_message is a plain synchronous method. Awaiting it raises TypeError — but the call sat inside a broad exception handler, so the message went out and a failure that had not happened was logged anyway.

Lesson

A broad except around an operation that must never break a live call is correct — but it will also hide your own mistakes. Worth pairing with checking the log actually stays quiet.

Process

A continuous integration check that could never pass

Symptom

The retrieval-quality job failed on every run since it was written.

Cause

It ran a command-line tool that exits non-zero unless all 32 questions pass. The documented baseline is 28/32. It was mathematically incapable of succeeding.

Fix

Point the job at the pytest guard that already existed, which asserts a margin of 24/32.

Lesson

A check that cannot pass reports nothing. Worse, it teaches the team that red is normal — which is how a real failure gets ignored later. Green has to mean something. The same lesson recurred in Phase 4: a home internet connection's rotating IP blocked the test suite from reaching the database for a day, a fix was verified by hand with a standalone script instead of the suite, and the moment the suite could run again it found two regressions that fix had actually caused. The rule that stuck: if the suite cannot run, the commit is unverified — say so, and go back to it once it can.

Supply chain

Ten gigabytes of GPU libraries on a machine with no GPU

Symptom

A routine rebuild was about to fill a 30 GB disk with 7.3 GB free.

Cause

torch and torchaudio were pinned in requirements — captured by pip freeze on a Windows machine, never chosen. On Linux, pip resolves torch to the CUDA build: roughly 10 GB of GPU libraries destined for a 4 GB virtual machine that has no GPU.

How it was proven unnecessary

Not by assuming. Pip reported Required-by: as empty; faster-whisper runs on CTranslate2; the VAD in use is onnxruntime-based. A dependency scan showed every package mentioning torch does so behind an optional extra that was never installed.

Lesson

pip freeze captures what happens to be installed, not what is needed, and it captures it with the current platform's assumptions baked in. Verify before removing — and verify before keeping.

Vendor

A monitoring stack pinned to a version that could not do the job

Symptom

The prepared Langfuse deployment specified version 2. The tracing code exports OpenTelemetry.

Cause

OTLP ingestion only exists from version 3. The configuration had been written without an environment to test in and honestly labelled "unverified" — but nobody checked whether the chosen version could perform the task at all.

What it exposed

Upgrading revealed the real constraint: version 3 needs ClickHouse, Redis and object storage as well as Postgres — six containers, 16 GB recommended, against a 4 GB machine already running three services.

Lesson

"Unverified" can hide a fault that was checkable from documentation the whole time. A version pin is a capability claim.

Standards

The lighter alternative that could not read our data

Symptom

Arize Phoenix looked ideal — one container instead of six, no usage caps, self-hostable on the existing machine.

Cause

Checking what pipecat actually emits — gen_ai.*, the official OpenTelemetry GenAI conventions — showed Phoenix only understands Arize's own OpenInference convention. Their paid product added GenAI support; the free self-hosted one has an open issue for it.

Consequence

Traces would have arrived and rendered as anonymous spans with no model, no tokens and no cost — precisely what the task exists to produce.

Lesson

"Supports OpenTelemetry" is not one capability. Check which semantic conventions both ends speak, not just the wire protocol. This one was caught before any code was written for it.

Reliability

A first connection with no retry

Symptom

Intermittent total silence at the start of a session — hit four separate times in one day.

Cause

Reading the library source showed the speech service connects its websocket exactly once at startup with no retry. Pipecat's own reconnect logic covers a connection that drops after being established, not the first attempt. Direct timing tests confirmed the network path was genuinely variable — usually 0.15 s, occasionally over 6.

Fix

A subclass wrapping the initial connect with retry and backoff. Since the greeting is the first thing every session does, one slow attempt previously meant silence with no recovery.

Lesson

Retry logic often covers steady state and not startup. Startup is where a cold connection is slowest and most likely to fail.

Security

The tempting fix that would have exposed production

Symptom

The test job could not reach MongoDB Atlas. Atlas allowlists specific addresses; CI runners get a random one every run.

The wrong fix

Add 0.0.0.0/0 to the allowlist. One line, works instantly, and exposes the production database to the entire internet to make a test pass.

The right fix

Give CI its own throwaway MongoDB service container. It also removed a second risk nobody had noticed: the test teardown drops the entire database, and it had been pointed at a real cluster.

Lesson

When a security control blocks you, the question is what the control is protecting — not how to switch it off. This is worth rehearsing; interviewers ask it deliberately. The same lesson recurred fatally: a local test run, pointed at production by mistake, actually dropped the live database. Recovery meant restoring from the server's own automatic snapshots and rebuilding several bots from what could be reconstructed — the incident that led directly to the server's database login being permanently restricted to a role that cannot drop a database at all, regardless of what any future test does.

Deployment

The same deploy command reported success and changed nothing

Symptom

Two unrelated incidents, hours apart, identical underneath: a rotated API key the running service kept ignoring, and a fixed reverse-proxy route that stayed broken after the fix was deployed. Both times the deploy command printed success.

Cause

Bringing a container up compares its service definition — image, ports, declared environment — and does nothing if that is unchanged. Neither incident changed it: one was a value inside an env file, the other a config file mounted into the container. Both were correct on disk and neither was re-read, because from the orchestrator's point of view there was nothing to do.

Why it stayed hidden

The output says "Running" or "Started" where a real change says "Recreated" — one word, easy to read straight past, with no warning that the file you just edited is not the one in effect.

Fix

--force-recreate for an env change, a restart for a mounted config file, and — the habit worth keeping — verifying from inside the running container rather than trusting the deploy: reading the value back out of the process's own environment, and making a real authenticated request through the exact client the application uses. A convenience check gave a misleading answer here too: a bare curl reported a 403 that had nothing to do with the credential, because the provider's edge network rejects unfamiliar user-agents.

Deployment

Three days of fixes that never reached the server

Symptom

A new frontend feature was committed, pulled and built on the server. The page loaded without it, even after a hard refresh, while git log on the server showed the correct commit.

Cause

The build is tsc -b && vite build — a type-check of every file under src, then the bundle only if that passes. The frontend had gained its first tests three days earlier, and with them two new dev dependencies. The server's update routine was git pull && npm run build, never an install, so the type-check failed on the test files, && stopped, and the old bundle stayed on disk and was served as if nothing had happened.

Fix

Diagnosed by checking the artifact rather than the process — grepping the built bundle for a string only the new code contained, which came back 0 and pointed straight at Cannot find module 'vitest'. npm ci before every build, and the deploy guide gained an actual update procedure — it had only ever documented first-time setup, which is exactly how the missing install became the habit.

Lesson

A test suite verifies the code; it has no opinion on whether the artifact on the server was actually built from it. Two real fixes had been silently unshipped for three days on a server everyone believed was current.

Frontend

Every validation error said "[object Object]"

Symptom

Creating a test account with a short password failed with a red box reading [object Object] — no way to tell what was actually wrong.

Cause

FastAPI reports validation failures as a list of objects, and the API client wrapped it directly in new Error(err.detail). Error() stringifies its argument, and an array of objects stringifies to exactly that string.

The trap in the obvious fix

FastAPI echoes the submitted value back in its error response — printing the raw error "to be safe" would have put the user's own password on the screen.

Fix

One helper builds the message from the field name and the message text only, used at every error site, with a test asserting the password can never appear in the output.

Lesson

No test had ever sent the frontend a real validation failure. Backend tests correctly asserted the 422 was returned and stopped at the boundary — nothing checked what a person actually saw on the other side of it.

RAG search

One symptom, three stacked search failures

Symptom

A caller asked what was on page 50 of an uploaded PDF. The bot said it had no access to the file — fixed, deployed, retested, same failure, a different log line underneath it, twice more.

Layer one

The caller spoke in three short sentences with pauses between them; the search read only the last fragment, which had no page number in it.

Layer two

Pinecone's monthly rerank allowance was exhausted, and a full search — rerank included — ran on the words "warm up" at the start of every single call, spending the same exhausted allowance a second time before the caller had said a word. The fix's own retry logic then made things worse: the SDK retried a refused request three times with sleeps in between, inside a thread nothing could cancel, so the retrieval budget was spent entirely on a request that was never going to succeed.

Layer three

Looking a Pinecone index up by name is a real network round trip to its control plane, and it ran as a plain synchronous call directly on the event loop — measured on the server at 0.5 to 17.3 seconds, freezing the greeting and the caller's own turn alike.

Fix

Search the whole unanswered turn, not just the last fragment. A rerank-only client with retries off and its own short timeout, recorded in the same worker thread as the request so an outcome is never lost even after the caller stops waiting. Index setup moved into a worker thread under a lock, with idle connections kept open just under Pinecone's own timeout.

Lesson

Three genuinely independent faults produced one identical symptom, stacked, so every fix in turn looked like it had done nothing — the interesting part of this one is not any single bug, it's that "still broken after the fix" does not mean the fix was wrong.

Data integrity

The caller's own side of every conversation was never saved

Symptom

A saved conversation record showed the bot's reply in full and an empty string for what the caller had actually said — every one of 145 turns in the latest backup, going back to the day the feature was written.

Cause

The recorder read TranscriptionFrame, but it sits — correctly, for other reasons — after pipecat's user-turn aggregator, which consumes transcription frames itself rather than passing them downstream. The finished text of a caller's turn only ever arrives through a separate event nothing in the project was listening for.

Fix

A small function forwards that event straight to the recorder. Independent review found one more: the pending turn used to be cleared only after the database write returned, so a caller speaking again while the previous turn was still saving had those words silently erased on the reset.

Lesson

No test had ever run the recorder behind the real aggregator — existing tests either constructed frames by hand or inspected service ordering. A test exercising the real event, not a shape that merely resembles it, is what finally caught a bug that had been live since the feature shipped.

Observability

The logs that would have explained the bug were being thrown away

Symptom

Trying to diagnose a live defect from the container logs: 213 pipeline lines in the window, and not one tool-call line, on calls that demonstrably made tool calls.

Cause

Python block-buffers its output when it isn't writing to a terminal — exactly the case inside a container. Every call runs in its own worker process ended with terminate(), so a call's last log lines weren't delayed, they were discarded with the buffer.

Fix

One line, PYTHONUNBUFFERED=1, in the container image, with a test asserting it stays there.

Lesson

Nothing was broken for a caller, so nothing could fail a behavioural test — this is a class of defect a test suite has no opinion about at all. It only becomes visible on the day you actually need the logs and they aren't there, which is the worst possible day to find out.

Resilience

A backup voice that was designed, tested, and never actually on the server

Symptom

The text-to-speech provider ran out of credits mid-testing and every call went silent — on a system with a circuit breaker and a local backup voice built for exactly this. The breaker did its job, tripped correctly, logged every step. No call ever switched to the backup.

Cause

The fallback deliberately refuses a backup whose model files aren't already on disk — starting a several-hundred-megabyte download while a caller waits to be greeted would be worse than the outage. That check was right; the model files were simply never on that machine, because the one-time download script had never been run there.

The second gap it exposed

Running the download revealed the speech-recognition backup was landing in a machine-learning library's default cache, inside the container's own filesystem — the next routine rebuild would have deleted it and silently returned readiness to "not ready" until the next real outage found out.

Lesson

Every piece of code here was tested and every test was correct — none of them can see that the machine it runs on was never given the model files at all. That is a deployment step, not code, and no test knew where a third-party library caches by default, which is what actually decides whether a file survives a rebuild.

Likely questions

Answers in your own voice, each anchored to something specific you actually did.

Walk me through the architecture.

Audio comes in over WebRTC to a FastAPI backend. Pipecat orchestrates the stages as a frame pipeline: speech to text, then a retrieval step that searches the customer's uploaded documents, then the language model, then text to speech back over the same connection. The part worth knowing is that each call runs in its own operating-system process — so a crash in one call cannot take down the server or anyone else's call. On top of that, a warm pool of pre-started worker processes autoscales with demand, a Redis-backed capacity cap refuses new calls cleanly once the system is full, and circuit breakers fail cloud providers over to local models when they trip.

What was the hardest bug?

Database writes failing on Linux but working on Windows. The cause was that multiprocessing defaults to spawn on Windows and fork on Linux — a forked child inherits the parent's already-connected database client, bound to an event loop that does not exist in the child. What makes it a good story is the sequel: months later the regression test for that fix failed in CI, because the test itself had been left on the platform default and was forking.

How do you know your document search is any good?

I built a suite of 32 questions with known correct pages and run them through the real retrieval path. Baseline is 28/32. The guard asserts a margin of 24/32 rather than the exact number, because retrieval has genuine day-to-day variance and a test that chases noise gets switched off. Before that suite existed I was tuning search thresholds by feel, which means I could not tell whether a change helped.

Why reranking? Isn't vector search enough?

No, and I can show why. For one query, the correct chunk did not appear in the raw top five at all. Raw cosine scores clustered between 0.60 and 0.65 for good and irrelevant results alike, so no threshold could separate them. The reranker is a cross-encoder — it reads the query and candidate together rather than comparing two independent embeddings. Its scores spread from 0.0 to 0.9, and that spread is what makes a threshold possible.

Your CI couldn't reach the database. How did you fix it?

Atlas allowlists specific addresses and CI runners get a random one each time. The tempting fix is to allow all addresses — one line, works immediately, and exposes the production database to the internet to make a test pass. I gave CI its own throwaway database container instead. That also closed a risk nobody had spotted: the test teardown drops the whole database, and it had been pointed at a real cluster. That exact class of mistake actually happened for real later, from a local test run against production by accident — recovered from a snapshot, and it's why the production login is now permanently restricted to a role that cannot drop a database regardless of what any future test does.

How do you keep from being locked into one vendor?

Provider selection lives behind three factory functions, so switching speech or language providers is a settings change rather than a pipeline rewrite. The same principle covers monitoring: the tracing code speaks plain OpenTelemetry, so moving from hosted to self-hosted is three environment variables and no code. I try to make vendor decisions cheap to reverse — that is what makes them not lock-in. The same three factories paid for themselves a second time in the load-testing task: a fourth branch swaps in free local stand-in services for a full concurrency test, with zero changes to the real call path.

What does a conversation cost you?

Between $0.0003 and $0.0006 in language-model spend, measured from live traces. I should be precise about the limit: that figure is exact for the language model, because token counts arrive as standard OpenTelemetry attributes and get priced automatically. Speech recognition and synthesis bill per audio-second and per character, which are not token usage, so their consumption is recorded but not yet priced. An all-in figure needs those two rates applied.

How do you handle a provider outage mid-call?

A circuit breaker per provider trips after a run of failures inside a short window, and switches that request to a local backup — faster-whisper for speech recognition, Piper for the voice — but only if the backup's model files are actually installed on that machine. I proved this live rather than trusting the code: held the real Cartesia breaker open for three minutes and a real call was built on Piper, in its voice, with no restart. Getting there found a real gap first — the backup files existed in the repo but had never actually been downloaded onto the production server, so every earlier outage had failed over to nothing.

How would you load-test a system that costs money per call?

The three cloud providers already sit behind factory functions for a completely different reason — vendor swapping. A fourth branch on those same factories swaps in local stand-in services that behave like the real ones — same timing shape, same audible output the client checks for — so the exact same load-test harness can run a full concurrency ramp against the real server for free. That's how I found the real ceiling without spending anything: not memory, but the warm-worker pool's cold-start behaviour when several calls need a new process at the same instant.

Tell me about a defect that took more than one fix to actually solve.

A caller asking for the time got an answer 5.5 hours out. I fixed the clock to know the bot's timezone — same wrong answer. The clock's fix had shipped to a function nothing was calling, because a bot with its own configured tools drops every built-in, including the clock. Offered the clock unconditionally — the model then invented an argument the function doesn't take, because it read the name out of the docstring instead of the schema, and the framework crashed rather than filtering it. Three unrelated faults, one identical symptom, each fix looking like it had done nothing until the third one actually landed. The lesson I lead with: "still broken after the fix" does not mean the fix was wrong.

What would you do differently?

Deploy sooner, and test the actual platform's behaviour rather than trust what's documented about it. Deploying early found three bugs no amount of local testing would have — the fork issue, the browser never being told about the relay, and the relay handing out unreachable addresses. Later, a written claim that Docker restarts an unhealthy container turned out to be flatly false on plain Docker without an orchestrator — proven by running two throwaway containers on the real server and watching one sit at zero restarts for forty seconds. I'd check platform behaviour directly earlier, rather than after building a whole recovery mechanism on top of an assumption.

What's not finished?

Phase 5 onward — organisations and roles, billing, the commercial layer that lets a company actually pay for this.
