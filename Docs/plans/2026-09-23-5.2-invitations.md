# Task 5.2 — Invitations Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin can invite someone to an organisation by email address; the invitee opens a link, signs in or signs up, and joins with the role they were given.

**Architecture:** A new org-scoped `Invitation` document holds the invitee's email, the role offered, a hash of a random token, and an expiry. The raw token is returned to the admin exactly once, as a shareable link. The invitee opens `/invite/:token`, which is a PUBLIC frontend route, sees who invited them, signs in or registers, and accepts. Delivery is by hand in 5.2 — the admin copies the link and sends it however they like — behind a `deliver_invitation()` seam that task 7.10 fills in when the app gains the ability to send email.

**Tech Stack:** FastAPI, Beanie/Motor on MongoDB Atlas M0 (no usable transactions), React 19 + Vite + TS + Tailwind 4, vitest + @testing-library, pytest.

**Spec:** `Docs/specs/2026-09-19-organisations-teams-roles-design.md` — 5.2 extends the organisation model it defines. The manual's 5.2 entry lists five steps; **steps 4 (enforce permissions on every route) and 5 (remove members, change roles) were completed in 5.1** and are out of scope here.

## Global Constraints

Every task's requirements implicitly include this section.

- **Never fetch-then-compare for tenancy.** Fetch a resource by id AND org_id in ONE query. This is the rule the whole of 5.1 is built on; breaking it is a cross-customer data leak.
- **Status-code order on org routes:** 401 (not logged in) → 400 "Choose an organisation" → 404 "Organisation not found" → 403 "Your role (`<role>`) can't do this". Reuse the existing `require_role(minimum, *, from_path=True)` from `app/core/org.py`; do not write new role checks.
- **Uniform responses on anything that takes an email.** Never reveal whether an email address has an account. Every outcome of "invite this address" returns the same status and the same body shape.
- **Every new stored model joins `ALL_MODELS`** in `app/models/registry.py`, and must either carry `org_id` or be listed in `ORG_EXEMPT_MODELS` with a reason. `tests/test_org_models.py` enforces this and WILL fail otherwise.
- **No transactions.** Atlas M0 has none usable. Any multi-document change must be safe when interrupted at any point, and must say in a comment which way it fails.
- **TDD.** Write the failing test, run it, watch it fail for the right reason, then implement. No production code without a failing test first.
- **Do not weaken a test to make it pass.** If a test cannot be satisfied, say so in the report rather than monkeypatching the thing under test into always failing or always passing.
- **Commit at the end of each task** with a message explaining WHY, not what.
- **Backend checks:** `./venv/Scripts/python.exe -m pytest -q` and `./venv/Scripts/python.exe -m ruff check .` from `backend/`, both clean.
- **Frontend checks:** `npm run test`, `npm run lint`, `npm run build` from `frontend/`, all clean.
- **NEVER run pytest against a non-test database.** The test teardown drops `DB_NAME`. `backend/.env` is already pointed at test databases; do not change it.

## Decisions already made (do not re-litigate)

1. **Delivery is by hand in 5.2.** The app shows the admin a link to copy. No email is sent. `deliver_invitation()` exists as a seam and does nothing but log.
2. **The token is random, not a JWT.** `secrets.token_urlsafe(32)`. Only its SHA-256 hash is stored, so a database leak yields no usable invitation links. The raw token is returned exactly once, at creation.
3. **Invitations expire after 7 days** (`INVITATION_EXPIRY_DAYS = 7`), per the manual's tip: an invitation link that works forever, sitting in an old inbox, is a security problem after someone leaves a company.
4. **`POST /orgs/{org_id}/members` becomes invitation-creating.** It no longer adds an existing user directly, and it no longer returns 404 "No Voix account uses that email" — that leak is the defect 5.2 exists to close (spec, "Email enumeration ... fixed by 5.2's invitation wording").
5. **Accepting requires the signed-in user's email to match the invited address** (compared after the same normalisation the users index uses). The link is a bearer credential; matching limits the damage if it is forwarded or leaks. A mismatch gets a clear, non-leaking error.

```python
# app/models/invitation.py
class Invitation(Document):
    org_id: str
    email: str                      # normalised, lowercase
    role: Role                      # "viewer" | "member" | "admin" | "owner"
    token_hash: str                 # sha256 hex of the raw token
    invited_by: str                 # user id
    status: str = "pending"         # "pending" | "accepted" | "revoked"
    expires_at: datetime
    created_at: datetime
    accepted_at: datetime | None = None
    accepted_by: str | None = None  # user id

# app/services/invitations.py
INVITATION_EXPIRY_DAYS = 7
class InvitationError(Exception): ...
class NotFoundError(InvitationError): ...      # unknown, expired, revoked, already used
class EmailMismatchError(InvitationError): ...
class AlreadyMemberError(InvitationError): ...

def hash_token(raw: str) -> str
async def create_invitation(org_id: str, email: str, role: str, invited_by: str) -> tuple[Invitation, str]
async def find_valid(raw_token: str) -> Invitation      # raises NotFoundError
async def accept(raw_token: str, user) -> Invitation    # raises NotFoundError / EmailMismatchError / AlreadyMemberError
async def revoke(org_id: str, invitation_id: str) -> bool
async def list_pending(org_id: str) -> list[Invitation]
async def deliver_invitation(invitation: Invitation, url: str) -> None
```
