The path

What happens when someone speaks

A caller says one sentence. Between their microphone and the reply they hear, it passes through eight stages. Each stage is a decision, and each decision has an alternative that was considered and rejected.

01

Getting the audio there

WebRTC · aiortc · coturn

The browser captures the microphone and streams it to the server as it is spoken — not as a file uploaded afterwards.

Why this
WebRTC is the only browser technology built for live, low-latency, two-way audio. Anything file-based adds seconds before a word is even heard.
Instead of
WebSockets carrying raw audio — workable, but you rebuild jitter buffering, packet loss handling and echo cancellation yourself.
The catch
WebRTC needs UDP and a TURN relay (coturn) for callers behind restrictive networks — mobile data especially. This is the reason the project runs on a plain VM instead of a serverless host.
02

Noticing that someone is speaking

Silero VAD

A small model watches the audio and decides, moment to moment, whether the sound is human speech or just noise.

Why this
Runs locally in milliseconds, costs nothing per call, and scores speech probability rather than mere loudness — so a slammed door doesn't register as talking.
Instead of
A volume threshold. Simple, and wrong: it cannot tell a loud room from a quiet voice.
Tuned to
confidence 0.6, set from measurements, not guesswork — real speech scores 0.92–0.99 on this microphone, background noise 0.18–0.43.
03

Deciding they have finished

Smart Turn v3 · ONNX

The hardest problem in voice. A pause mid-sentence is not the same as being done, and answering into a pause is what makes bots feel robotic.

Why this
A classifier that listens to how the sentence trailed off — intonation, not just silence — so "I'd like to book…" is recognised as unfinished.
Instead of
A fixed silence timer. Too short and it interrupts; too long and every reply feels sluggish. There is no value that is right for both.
Runs
Locally as an ONNX model inside the call process — no network round-trip in the most latency-critical decision in the system.
04

Turning speech into text

Deepgram · Whisper fallback

Streaming transcription: words arrive as they are spoken, refined as more context arrives, then finalised.

Why this
Genuinely streaming, strong on Indian-accented English and Hindi, and exposes endpointing — control over how long a pause must be before a sentence is closed.
Instead of
OpenAI Whisper API, which transcribes complete audio files — excellent quality, unusable for live conversation.
Also built
Local faster-whisper behind the same interface, so the system can run with no speech vendor at all.
05

Finding the relevant documents

Pinecone · hybrid + rerank

The caller's question is matched against their uploaded documents, and the best passages are handed to the AI along with the question.

Why hybrid
Two indexes are searched at once. Dense vectors find meaning ("refund policy" ≈ "money back"); sparse keyword search finds exact strings — order numbers, part codes — that embeddings represent poorly.
Why rerank
Raw similarity scores cluster tightly: good and irrelevant matches both land around 0.6, so no threshold separates them. A cross-encoder reads the question against each candidate and spreads scores 0.0 to 0.9, which makes a real cut-off possible.
Also
Spoken questions are rewritten before searching — "umm what about the second one" is not a search query.
06

Thinking of a reply

Groq · gpt-oss-120b

The language model receives the conversation, the retrieved documents and the available tools, and writes the answer.

Why Groq
Speed, and only speed. Groq runs open models on custom silicon and starts replying in roughly 80ms where a conventional host takes 400ms. In a voice call that difference is audible.
Instead of
GPT-4o directly — better at hard reasoning, but the added latency is felt on every single turn. It stays available as a per-bot setting.
The principle
Below about 800ms a reply feels conversational; past 1.5s it feels like a machine. Latency is the product, not a metric.
07

Speaking it aloud

Cartesia Sonic · Piper fallback

Text becomes audio and streams back while the rest of the sentence is still being generated.

Why this
First audio in 60–100ms, measured live, and genuinely multilingual — the same system speaks Hindi, French and Spanish with native voices.
Instead of
ElevenLabs (higher quality, higher latency and cost) or cloud TTS from Google/Azure (slower to start speaking).
Free path
Piper runs locally at no cost with a Hindi voice, switchable with one setting — the answer to "what happens when the credits run out".
08

Holding it all together

Pipecat 1.7

The framework that connects all of the above as a pipeline of processors, with audio flowing through as frames.

Why a framework
Turn-taking, interruption, frame ordering and back-pressure are each subtle enough to get wrong. Pipecat solves them and leaves the domain logic to you.
Instead of
LiveKit Agents or a hand-rolled asyncio pipeline. Hand-rolling means owning barge-in and interruption semantics forever.
Worth saying
Custom processors were still written on top of it — Markdown stripping, transcript recording, and retrieval placement.

Design decisions

Choices worth defending

These are the parts an interviewer will probe, because each one has a real trade-off behind it.

One process per call

Every call runs in its own operating-system process rather than sharing one. A crash takes down that call and nothing else.

"How do you stop one bad call taking out the server?"

A pool of warm workers

Starting a process means loading the whole audio stack — 13.7s cold. Processes are started before anyone calls, so claiming one takes 0.04s.

"Where did your latency actually go?"

A provider layer, not direct calls

Nothing calls Deepgram or Cartesia directly. A factory returns whichever provider configuration names, so cloud and local swap with no code change.

"What if a vendor doubles their price?"

Retrieval after turn assembly

Document search was firing on half-sentences, because it sat before the component that assembles a complete turn. Moving it after made the bug structurally impossible.

"Tell me about a bug that changed your design."

Spawn, never fork

Linux defaults to fork for new processes; the database client inherits a dead event loop and every call fails. Forcing spawn everywhere makes Linux behave like the machine it was written on.

"Something that only broke in production?"

Language reaches all three layers

A bot's language must reach transcription, speech synthesis and the model's prompt. Reaching only two produced a bot that heard Hindi and answered in English.

"How do you handle multiple languages?"

War stories

Bugs worth telling

"Tell me about a difficult bug" is asked in almost every interview. These are real, they were found in production logs, and each has a transferable lesson.

Two bots answered the same caller

A caller heard two voices talking over each other — one replying in Hindi that it could hear them, the other in English that it could not speak. The logs showed two complete pipelines running for one call, each with its own conversation history. A second connection had been created without the first being closed, leaving it live but unreachable from the page that made it.

Fixed on both sides. The client stopped creating the second connection; the server stopped being willing to run two — because the server must hold even when the client misbehaves.

Settings that were silently ignored

Passing language="hi" to the speech service did nothing. No error, no warning — the value was discarded and the default kept, so every Hindi call was transcribed and synthesised as English. The same pattern was eventually found in four different places in the codebase.

A configuration value that silently fails to apply produces no error and no log line. Tests now assert on the constructed object, not just that construction succeeded.

Sentences cut in half

Callers' sentences were being split mid-thought, with the second half arriving as a separate question. Two rounds of fixes to the transcription settings changed nothing. The real cause: the speech detector was never firing at all, so the framework silently fell back to guessing turn boundaries from transcripts.

The debug logging was itself wrong — it labelled a different event as "VAD", so the logs asserted a component was working while it was completely idle. Instrumentation was added to measure the real values; the threshold was then set by arithmetic rather than a fourth guess.
