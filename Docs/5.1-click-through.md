# 5.1 Organisations (Plan B) — local click-through

This is Step 4 of Task 9, for you to run by hand. It needs a running
backend, a running frontend dev server, and two real accounts. Nothing
here is automated — that is deliberate (see rules.md for this plan): an
agent may not start the backend or touch any server.

## Start the backend

From `backend/`, with the virtualenv already set up (`backend/venv`) and
`backend/.env` already configured:

```bash
cd "D:\Voice Agent\backend"
venv/Scripts/uvicorn main:app --reload --port 8080
```

This matches how `deploy/Dockerfile` runs it in production (`uvicorn
main:app --host 0.0.0.0 --port 8080`), just with `--reload` for local work
and the default host (`127.0.0.1`), which is all the frontend dev proxy
needs.

## Start the frontend

From `frontend/`, in a second terminal:

```bash
cd "D:\Voice Agent\frontend"
npm run dev
```

This starts Vite on `http://localhost:5173` and proxies `/auth`, `/bots`,
`/connect`, `/documents` and `/orgs` through to the backend on port 8080
(see `frontend/vite.config.ts`) — open `http://localhost:5173` in your
browser once both are up.

**Note:** while preparing this document, Task 9 found and fixed a gap:
`/orgs` was missing from that proxy list, which would have made every
check below fail at step 1 (the page would never get past loading). That
fix is already committed. The same path was also missing from
`deploy/Caddyfile`'s production proxy list — outside this plan's scope
(`deploy/` is not `frontend/`) to fix here, but it has since been fixed
separately (commit `3a7becd`).

## Accounts needed

Two real accounts, both members of the **same** organisation:

- **Account A** — the **owner** of that shared organisation.
- **Account B** — added to that organisation as a **viewer**.

Sign in as each in a separate browser (or one normal window + one private/
incognito window) so both sessions are live at once for the checks that
need them side by side.

---

## The eight checks

Do these in order. For each: what to do, then what should happen. If
anything does not behave as described, note it — don't adjust anything to
make it pass.

### 1. Signing in lands you under an organisation address

Sign in as the owner (Account A).

**Expect:** the address bar shows `/o/<some-id>/dashboard` — never a bare
`/dashboard`. `<some-id>` is whichever organisation was last used, or a
personal one if there's no "last used" yet.

### 2. Create, upload, talk, cite — all inside that organisation

Still as the owner: create a bot, upload a document to it, start a call
and talk to it, then open a citation the bot gives you during the call.

**Expect:** all of it works normally — the bot is created, the document
uploads, the call connects, and the citation opens (it should show the
source document, fetched as a blob).

### 3. A second organisation starts empty

From the organisation switcher, create a second organisation.

**Expect:** the dashboard for the new organisation shows **no bots** — the
first organisation's bot must not appear here. (This is the core promise
of the whole feature: data doesn't leak across organisations.)

### 4. Switching organisations mid-call doesn't move the call

Start a call in organisation A (switch back to it first if you're not
already there). While the call is still running, use the switcher to move
to organisation B. Then, with the call still going, open a citation from
it.

**Expect:** the call keeps running the whole time — switching organisations
does not drop it. The citation still opens correctly, even though the
address bar and the rest of the page now show organisation B.

### 5. A viewer sees a restricted dashboard

Add Account B to organisation A as a **viewer** (from the Members page, as
the owner). Then, in the second browser/session, sign in as Account B and
go to organisation A.

**Expect:**
- No "New bot" button on the dashboard.
- No Approvals link and no Webhooks link anywhere in the nav.
- The viewer *can* still open a bot and talk to it (starting a call is not
  an admin action).

### 6. Visiting an organisation you're not a member of sends you to the chooser, not to login

Still signed in as Account B (the viewer), edit the browser's address bar
directly to point at an organisation id Account B is **not** a member of
(e.g. organisation B's id, if you didn't add B to it).

**Expect:** you land on the organisation chooser page — not a login
screen, and not an error page. Account B is still signed in; it's just not
a member of that particular organisation.

### 7. An old-style address redirects

With either account signed in, edit the address bar to the old, pre-org
path: `http://localhost:5173/dashboard` (no `/o/<id>` prefix).

**Expect:** you're redirected to the equivalent address under an
organisation (your last-used one, or your personal one) — you should not
see a raw `/dashboard` with no organisation in the URL, and you should not
see a broken or blank page.

### 8. The last owner can't leave

As the owner (Account A), on the Members page for an organisation where
you are the *only* owner, try to remove yourself / leave the organisation.

**Expect:** the action is refused, and the server's own message is shown
to you on the page (not a generic error, not a silent no-op) — an
organisation always needs at least one owner.
